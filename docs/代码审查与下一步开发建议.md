## 3. 技术债(建议优先处理)

### 3.1 组件反向依赖父节点(中等风险,最该修)

`chest.gd`(L49-54)、`save_point.gd`(L12-14)、`enemy.gd`(L144-146)都通过 `get_parent().has_method("spawn_potion")` 反向调用主场景。

问题:
- 组件无法独立实例化(违反"每个场景可独立运行"原则)
- 父节点改名/重构即静默失效
- 敌人由刷怪器生成时父节点是 Spawner,`has_method` 会悄悄返回 false,掉落静默丢失

改法:组件向上发信号,主场景监听。

```gdscript
# chest.gd
signal potion_requested(pos: Vector2, item: ItemData)
# _open() 中: potion_requested.emit(global_position, ItemData.red_potion())
```

### 3.2 玩家引用每帧全树查找(敌人增多时会痛)

`enemy.gd` `_get_player()`(L87-88)每帧 `get_first_node_in_group("player")`,刷怪上限 14 时还能忍,但阶段 2 敌人量级上来就是纯浪费。

改法:在 `_ready()` 缓存一次引用,或由 Spawner 注入。

### 3.3 碰撞层不一致(隐患)

- 场景手放的敌人 `collision_layer = 2`(main.tscn)
- 刷怪器 `_create_enemy()`(spawner.gd L55-83)生成的敌人**没有设置 collision_layer**,默认 layer 1

后果:手放敌人和刷怪敌人互不碰撞,行为不对称。建议:
1. 在 project.godot 给物理层命名(世界=1、敌人=2、箭矢=4,当前正好是这个分配,只是没文档化)
2. 刷怪器生成敌人时显式设置 `collision_layer = 2`

### 3.4 类型安全未补齐(小改,收益大)

| 位置 | 现状 | 建议 |
| --- | --- | --- |
| player.gd L47 | `var quickbar: Array` | `Array[ItemData]` |
| player.gd L48 | `var equipment := {...}` | `Dictionary[String, ItemData]` |
| player.gd L46 | `var skill_levels := {...}` | `Dictionary[String, int]` |
| enemy.gd L16 | `@export var patrol_points: Array` | `Array[Vector2]` |
| main.gd L43 | `var fixed := [...]` | 显式类型数组 |
| hud.gd | 大量 UI 成员变量 | 逐个补齐类型 |

### 3.5 单体脚本膨胀(阶段 2 的门槛)

- `player.gd` 421 行:移动、射击、技能×2、装备、快捷栏、等级、受击、动效全在一个类
- `enemy.gd` 147 行:巡逻、索敌、攻击、掉落、动效混在一起
- `hud.gd` 334 行:纯代码构建 UI

**阶段 2 要加魔法师和新敌人,这个结构会膨胀到不可维护。**建议在加新职业前先做两个抽象:

1. **职业抽象**:`class_name Ranger extends PlayerClass` / `Player` 持有职业实例,技能、基础属性、攻击方式由职业决定。当前 `_fire_arrow`、`_try_triple_shot`、`_try_draw_speed` 全部硬编码在 player.gd,魔法师无法复用。
2. **敌人行为**:巡逻/索敌抽成 `PatrolBehavior` / `ChaseBehavior`(或状态机),新增"远程怪"只需换攻击行为。

### 3.6 UI 纯代码构建(低优先级)

hud.gd 用代码拼了 4 个面板,改样式要改代码。Godot 的 Theme 资源 + .tscn 场景是正路,但重构成本高,**建议阶段 2 中期再做,不要现在动**。
